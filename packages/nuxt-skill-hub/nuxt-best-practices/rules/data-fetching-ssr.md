## Data Fetching and SSR

### `data-usefetch-or-asyncdata-for-initial`: Use `useFetch`/`useAsyncData` for initial render data
**Apply when:** building SSR pages or route-level data loading.
**Skip when:** the call is explicitly client-only and not SEO-critical.

```vue
<!-- Wrong: runs on server and again on client -->
<script setup lang="ts">
const posts = await $fetch('/api/posts')
</script>
```

```vue
<!-- Right: payload-backed, no second request on hydration -->
<script setup lang="ts">
const { data: posts } = await useFetch('/api/posts')
</script>
```

**Why:** `$fetch` is for event-driven calls (submit, click). Initial view data should go through the payload: `useFetch` for one HTTP call, `useAsyncData` for custom logic or composing several requests.
**Verify:** no setup-time `$fetch` for first-render data; the network tab shows no repeat request during hydration.

### `data-stable-keys-and-option-consistency`: Keep async-data keys explicit and option-consistent
**Apply when:** sharing `useAsyncData` or `useFetch` state across components or composables.
**Skip when:** each call site truly needs isolated state.

```ts
// Wrong: the autogenerated key comes from this file and line,
// so every caller shares one entry whatever the id
export const useUser = (id: Ref<string>) =>
  useAsyncData(() => $fetch(`/api/users/${id.value}`))
```

```ts
// Right: explicit key derived from the input
export const useUser = (id: Ref<string>) =>
  useAsyncData(() => `user:${id.value}`, () => $fetch(`/api/users/${id.value}`))
```

**Why:** calls sharing a key share state. Nuxt warns when they disagree on `transform`, `pick`, `deep`, or similar options, and unstable keys cause confusing reuse.
**Verify:** keys are unique per resource; every call site using the same key passes the same options.

### `data-side-effects-via-callonce`: Keep `useAsyncData` handlers side-effect free
**Apply when:** a data loader also triggers analytics, store mutations, or one-time bootstrapping.
**Skip when:** a third-party API couples the side effect to the fetch and it cannot be split.

```vue
<!-- Wrong: the store write replays on refresh, watch, and navigation -->
<script setup lang="ts">
const { data } = await useAsyncData('user', async () => {
  const user = await $fetch('/api/me')
  store.setUser(user)
  return user
})
</script>
```

```vue
<!-- Right: one-time bootstrap through callOnce -->
<script setup lang="ts">
await callOnce('user', () => store.fetchUser())
</script>
```

**Why:** `useAsyncData` handlers re-run on `watch`, `refresh()`, and navigation, replaying anything embedded in them.
**Verify:** handlers only compute and return data from their inputs; store writes go through `callOnce`, analytics through event handlers.

### `data-reactive-url-not-watch-only`: Use reactive URL/options, not `watch` alone, for parameterized fetches
**Apply when:** fetching data from reactive route params, filters, or query inputs.
**Skip when:** the endpoint must stay fixed while unrelated state changes.

```vue
<script setup lang="ts">
const route = useRoute()
const page = ref(1)

// Wrong: the URL string is built once; watch refetches the same endpoint
// useFetch(`/api/products/${route.params.id}`, { watch: [page] })

// Right: getter URL and ref options are watched automatically
const { data } = await useFetch(() => `/api/products/${route.params.id}`, { query: { page } })
</script>
```

**Why:** reactive `query`/`params` and getter or computed URLs are watched by default. Use `watch: false` only to opt out on purpose.
**Verify:** changing each reactive input changes the request URL or query and refreshes `data`.

### `data-minimize-payload-shape`: Minimize payload transfer for SSR data
**Apply when:** fetching large objects or arrays where the first render needs a subset.
**Skip when:** consumers in the same render boundary need the full object.

```vue
<script setup lang="ts">
// Wrong: useFetch('/api/users') puts full user records in the payload

// Right: only what the template reads is serialized
const { data: users } = await useFetch('/api/users', {
  transform: list => list.map(({ id, name }) => ({ id, name })),
})
const { data: me } = await useFetch('/api/me', { pick: ['id', 'name'] })
const { data: recs } = useFetch('/api/recommendations', { lazy: true, server: false })
</script>
```

**Why:** `pick`/`transform` shrink what goes into the HTML payload, not what the upstream API returns. Trim at the API if the upstream response is the problem.
**Verify:** compare the payload (DevTools Payload tab or `window.__NUXT__`) against fields the template actually uses.

### `data-serialization-boundary-awareness`: Respect serialization differences between payload and API routes
**Apply when:** returning non-primitive values (Date, Map, Set, class instances) through SSR data or server API routes.
**Skip when:** the upstream contract requires runtime-only values that never cross a boundary.

```ts
// app: useAsyncData payload uses devalue, so Date/Map/Set survive
const { data } = await useAsyncData('now', async () => ({ at: new Date() }))

// server/api/event.get.ts: JSON, so Date becomes a string and Map/Set become {}
export default defineEventHandler(async () => {
  const row = await getEvent()
  return { startsAt: row.startsAt.toISOString(), tags: [...row.tags] }
})
```

**Why:** the Nuxt payload is serialized with `devalue`; server route responses use JSON, which supports fewer types.
**Verify:** check returned types in both `useAsyncData` handlers and `server/api/*`; normalize API output (or add `toJSON`) so the client gets the shape its types claim.
